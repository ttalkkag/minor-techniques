# 저장 중단과 버전 변경에서도 복원할 상태 남기기

[그룹 요약](../README.md) · [리서치](research.md)

## 저장은 어떤 순간의 무엇을 남기는가

화면을 그리는 모든 값을 저장하면 크기가 커지고 필요 없는 자산도 중복된다. 반대로 위치만 남기면 획득 아이템·열린 문·이미 소비한 보상을 재구성할 수 없다. 먼저 저장 후 복원할 플레이 상태의 범위를 정해야 한다.

교육용 작은 세계라면 플레이어 ID·위치·인벤토리·이벤트 플래그와 스키마 버전을 저장한다. RNG까지 복원하면 다음 추첨의 재현 범위도 달라진다. 게임 진행 중 각각의 값을 따로 읽는 대신 한 시점의 일관된 상태를 복사해야 한다. 아이템을 지급한 뒤 플래그를 읽고 인벤토리는 지급 전 값을 읽으면 실제로 없었던 조합이 저장될 수 있다.

## 비트 압축도 계약이 필요하다

16개 이벤트를 16바이트짜리 0/1 배열로 두는 대신 2바이트에 담을 수 있다. 이벤트 i의 바이트 위치는 floor(i/8), 마스크는 1 << (i mod 8)이다. 예를 들어 이벤트 0과 3만 켜진 첫 바이트는 00001001, 십진수 9다. JSON 표현과 비교할 때는 공백·키·문자 인코딩까지 포함한 실제 바이트 수를 센다.

이벤트 번호가 바뀌면 같은 비트가 다른 사건을 뜻하게 된다. 단순히 새 배열 순서로 읽지 말고 버전별 번호표나 마이그레이션으로 의미를 보존한다. 압축률이 높다는 사실은 호환성이 유지된다는 뜻이 아니다.

## 이전 정상본을 보존하는 이중 슬롯 모델

슬롯 A에 세대 7의 정상 저장본이 있고 B를 세대 8로 갱신한다고 가정한다.

1. 저장 세대 8의 상태를 고정한다. 동시에 온 요청은 순서를 정해 큐에 넣거나 합치는 규칙을 적용한다.
2. A를 건드리지 않고 B에 버전·세대·길이·본문·검사값을 쓴다.
3. 저장 API의 완료 규약을 처리하고, B를 읽어 구조·길이·검사값·지원 버전을 확인한다.
4. 복원 때 A와 B를 각각 검증하고 지원 가능한 유효 세대 중 최신을 고른다.
5. B가 중간에 끊겼다면 A의 세대 7로 돌아간다. 다음 저장도 확인된 정상본을 먼저 보존한다.

이 절차는 교육용 저장 장치 모델이다. 실제 원자성·쓰기 순서·영속화 보장은 파일 시스템과 플랫폼 API에 달렸다. 완료 표시 하나를 썼다는 사실만으로 실제 전원 차단에 안전하다고 할 수 없다. 읽기 재검증도 운영체제 캐시의 내용을 볼 수 있으므로 비휘발성 저장소로의 영속화를 대신하지 않는다. 이 구분은 [SQLite의 원자적 커밋 설명](https://sqlite.org/atomiccommit.html)의 쓰기·flush 단계에서도 확인할 수 있다.

| 실패 지점 | 기대하는 복구 규칙 | 남는 한계 |
|---|---|---|
| B 본문 일부만 기록 | B 거부, A 선택 | 최근 진행은 잃음 |
| B 검사값 불일치 | B 거부 | 체크섬이 검출 못 하는 손상 가능성 별도 |
| B는 정상이나 새 버전 미지원 | 이전 지원본 선택 또는 명시적 오류 | 무조건 최신 세대를 읽으면 안 됨 |
| 두 슬롯 모두 손상 | 복구 실패를 알림 | 초기화로 조용히 덮지 않음 |
| 세대 8보다 7 요청이 늦게 완료 | 저장 순서 관리로 퇴행 방지 | 비동기 완료만 믿으면 순서 역전 |

## 비동기와 안전성을 분리하기

비동기 저장은 쓰는 동안 게임 진행을 덜 막기 위한 선택이다. 성공 콜백을 무시하거나 같은 객체를 계속 변경하면 일관성 문제는 남는다. Epic은 SaveGame 객체에 저장 데이터를 담고 비동기 완료의 성공/실패를 받는 경로를 설명한다. 작은 저장이나 메뉴에서는 동기도 선택할 수 있다. [Epic Saving and Loading](https://dev.epicgames.com/documentation/en-us/unreal-engine/saving-and-loading-your-game-in-unreal-engine)

체크섬은 손상 감지이며 최신성·인증의 보증이 아니다. 자동 저장과 수동 저장도 실패 복구와 별도 정책이다. 저장 아이콘은 요청 시작, 쓰기 완료, 실패를 구분해야 한다.

## 적용 조건과 남은 일

작은 상태에는 읽기 쉬운 포맷이 조사와 수정에 유리하다. 크기·복잡한 자료형이 문제가 될 때 바이너리 포맷을 비교한다. 원작 카트리지 용량과 실제 포켓몬 저장 레이아웃은 이 모델의 수치로 사용하지 않았다.

구현 시에는 각 쓰기 단계의 중단, 역순 완료, 잘린 길이, 미지원 버전, 이전 버전 변환을 보여 주면 원인이 드러난다. 이 문서는 그런 장애 주입의 설계이며 실제 장치 전원 차단 시험 결과는 없다.
