# 진행 상태를 사람이 적는 문자열로 저장하기

[그룹 요약](../README.md) · [리서치](research.md)

## 짧은 코드가 무엇을 포기하는가

레벨과 아이템을 복원하면서 정확한 위치·전투 중 효과·난수 상태를 버리면 짧은 코드를 만들 수 있다. 다시 시작할 위치가 고정인 것은 복원 오류일 수도 있지만 처음부터 저장하지 않는 규칙일 수도 있다. 보존 범위를 정한 뒤 인코딩을 설계해야 한다.

문자표 크기가 A이고 길이가 n이면 이론상 최대 용량은 n×log2(A)비트다. 예를 들어 32개 문자로 4글자를 쓰면 20비트를 표현한다. 버전과 검사값도 이 20비트 안에 들어가므로 전부 플레이 상태에 쓸 수 없다.

## 손으로 따라가는 교육용 포맷

원작 포맷과 무관한 20비트 예제를 다음과 같이 정한다.

| 필드 | 비트 수 | 허용 값 |
|---|---:|---|
| 버전 | 2 | 현재 0만 지원 |
| 레벨 | 4 | 1–12, 나머지는 거부 |
| 아이템 | 8 | 각 비트에 하나의 보유 여부 |
| 검사값 | 6 | 아래 예제 계산값 |

순서는 버전→레벨→아이템→검사값으로 고정한다. 계산을 보기 쉽게 검사값을 `(버전 + 레벨 + 아이템 값) mod 64`로 둔다. 이것은 좋은 오류 검출 코드를 추천하는 것이 아니라 체크섬의 한계를 드러내는 단순 합이다.

버전 0, 레벨 5, 아이템 값 3이면 검사값은 8이다. 비트열 `00 0101 00000011 001000`은 5비트씩 `00010 10000 00110 01000`으로 나뉜다. 각 묶음의 값은 2,16,6,8이다. 32개 문자표 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`의 0부터 시작한 인덱스로 바꾸면 `2G68`이 된다. 문자표는 [Crockford Base 32](https://www.crockford.com/base32.html)와 같다. 필드 배치와 6비트 합계 검사값은 자체 예제이며, Crockford의 선택적 modulo 37 검사 문자나 악마성 2 포맷은 사용하지 않는다.

## 읽는 순서가 중요한 이유

1. 길이가 정확히 4인지, 문자표에 없는 문자가 있는지 확인한다.
2. 문자 인덱스를 5비트씩 복원해 20비트로 합친다.
3. 검사값을 분리해 계산값과 비교한다.
4. 지원 버전인지 확인한 뒤 필드 범위를 확인한다.
5. 허용된 상태로 초기 장면을 생성한다. 저장하지 않은 위치·일시 효과에는 정해 둔 초기값을 적용한다.

같은 합을 만드는 변화를 생각하면 약점이 보인다. 레벨을 5→6, 아이템을 3→2로 바꾸면 합은 여전히 8이다. 단순 합은 이 변경을 잡지 못한다. 데이터와 검사값을 함께 다시 계산할 수도 있다. 난수를 덧붙여 코드가 매번 달라져도 이 문제가 자동 해결되지는 않는다.

## 오류 검출과 인증의 선택

오타 검출은 실수로 변한 문자열을 알아내는 목적이다. 메시지 인증은 키를 가진 주체가 만든 데이터인지 확인하는 목적이다. HMAC은 비밀키를 이용하는 인증 구조이며 이 예제 합계와 목적이 다르다. [RFC 2104](https://www.rfc-editor.org/rfc/rfc2104)

플레이어가 직접 실행하는 클라이언트에 키를 넣었다고 온라인 보상 상태를 신뢰할 수 있는 것은 아니다. 이 실험은 인증 프로토콜을 만들기 위한 문서가 아니다. 개인 진행 코드, 퍼즐 정답, 제한된 공유 상태처럼 보존 범위가 작은 경우에 설명하기 적합하다.

현대 파일 저장에서는 필드 이름과 버전을 가진 구조를 비교할 수 있다. 입력 편의와 복원 범위를 넓히기 쉽지만 중단·호환성 문제는 [저장 시스템](../save-systems/analysis.md)에서 별도로 다룬다.

## 관찰과 한계

상태→코드→상태 왕복, 코드 한 글자 변경, 잘림, 미지원 버전, 범위 밖 레벨을 비교한다. 원상 복원이 되는 필드와 초기화되는 필드를 함께 보여 주면 저장 축약을 이해하기 쉽다. 이 예제 계산만 확인했으며 실제 악마성 2 포맷을 구현하거나 원작 코드로 검증하지 않았다.
