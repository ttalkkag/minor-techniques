## 외부 근거와 해석

[RFC 2104: HMAC](https://www.rfc-editor.org/rfc/rfc2104)의 개요와 정의를 09-25 재열람했다. 비밀키로 메시지 인증을 수행하는 구조라는 구분에 사용한다. RFC에 등장하는 역사적 해시 선택을 현재 보안 권장안으로 옮기지 않는다. 실제 인증 구현을 이 프로젝트가 제공한다는 의미도 아니다.

[Godot Saving games](https://docs.godotengine.org/en/stable/tutorials/io/saving_games.html)의 저장 상태 구성과 `JSON vs binary serialization`은 현대 파일 저장의 비교 기준이다. 필드를 명시적으로 남기고 복원해야 한다는 점을 확인한다. 파일로 바꾸는 것만으로 암호화·변조 방지가 생긴다고 설명하지 않는다.

두 자료는 서로 다른 목적을 보강한다. RFC는 인코딩과 인증의 혼동을 교정하고, Godot은 저장 매체가 문자열에서 파일로 바뀌어도 복원할 상태 정의가 필요하다는 비교를 돕는다.

## 문서에 채택한 자체 예제

20비트 레이아웃, `2G68` 예제와 단순 합 검사값은 독자가 손으로 따라갈 수 있도록 새로 구성했다. 32문자표는 [Douglas Crockford의 Base 32](https://www.crockford.com/base32.html)와 일치하며, 2026-09-26 원문 문자표와 `Check` 절을 확인해 자체 창작 범위에서 제외했다. 이 예제는 그 문서의 소문자·혼동 문자 허용 규칙과 선택적 modulo 37 검사 문자를 채택하지 않는다. 같은 합을 가진 서로 다른 상태가 존재하는 계산으로 손상 검출의 한계를 보여 준다.

기존 `qualified` 판정을 유지한다. 악마성 2의 실제 문자표·난수·필드·체크섬은 미확인이다. 실제 원작 설명으로 확대하려면 버전별 코드나 검증 가능한 역공학 자료가 필요하다.

## 열린 질문

공유 코드에 어떤 상태를 보존할지, 사람이 혼동하기 쉬운 문자를 제외할지, 오타를 단순 거부할지 복원까지 지원할지를 정해야 한다. 정식 실험에서는 필드 범위와 왕복 결과를 확인하고 원작 코드와 교육용 코드를 명확히 구분한다.
