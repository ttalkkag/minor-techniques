# 잔디의 제출·기하·픽셀 비용 분리

[그룹 요약](../README.md) · [조사 근거](research.md)

빽빽한 풀밭에서는 같은 “느리다”라는 현상에 CPU 제출, 정점 변형, 픽셀 중첩, 그림자 패스가 함께 기여한다. 이 중 무엇을 줄였는지 알 수 있어야 컬링·LOD·인스턴싱의 결과를 해석할 수 있다.

## 비용이 발생하는 단계

1. 풀의 위치와 바람 상태를 준비한다.
2. 해당 카메라·패스에 제출할 대상을 고른다.
3. 메시·재질별 명령을 제출하고 정점을 변형한다.
4. 화면에 덮인 영역의 텍스처·조명·투명도를 계산한다.
5. 주 화면과 별도로 필요한 그림자·반사 패스를 처리한다.

`제출 수`, `삼각형 수`, `픽셀 셰이더 호출`, `CPU/GPU 시간`은 서로 대체 가능한 지표가 아니다. [Unity GPU 최적화 지침](https://unity.com/how-to/gpu-optimization)은 overdraw, batch count, 카메라별 culling, LOD를 별도 항목으로 다룬다.

## 같은 장면을 다른 방법으로 줄이는 예

설명용으로 풀 1,000개에 각각 삼각형 8개가 있다고 하자. 전체는 8,000개다. 가시성 검사로 400개만 제출하면 3,200개가 되고, 그중 300개를 삼각형 2개의 LOD로 바꾸면 `100×8+300×2=1,400`개가 된다. 동일 자산을 인스턴싱해 제출 명령을 줄여도 이 1,400개 자체가 자동으로 사라지지는 않는다.

화면 100×100픽셀 영역에 카드 10장이 겹친다면 단순 모델의 후보 프래그먼트는 100,000개다. 실제 호출 수는 잘라내기·깊이·패스에 따라 달라진다. 이 예는 비용의 위치를 보여 주는 산술이며 프레임 속도나 절감률이 아니다.

## 해결 절차

| 관찰한 문제 | 먼저 바꿀 것 | 함께 확인할 것 |
| --- | --- | --- |
| CPU 명령 제출 비중이 큼 | 같은 메시·재질의 인스턴싱 | 배치가 깨지는 재질·상태 차이 |
| 먼 풀의 정점 처리가 큼 | 화면 점유율 기반 LOD | 전환 팝핑·그림자와의 차이 |
| 투명 영역이 넓고 겹침이 많음 | 카드 빈 영역·겹침·표현 밀도 | 잘라내기 경계와 시각 품질 |
| 가려진 풀도 계속 처리 | 해당 시점의 컬링 | 검사 자체 비용·재등장 지연 |

먼 풀을 반드시 카드로 바꿀 필요는 없다. 더 적은 메시, 표현 밀도 감소 등 후보를 같은 시점에서 비교한다. 컬링용 bounds는 바람으로 변형된 기하를 포함해야 하며, 주 카메라 밖이어도 그림자에 필요한 풀을 전역 삭제해서는 안 된다.

## 바람을 더했을 때의 추가 조건

자체 단순 모델은 밑동을 고정하고 높이 비율 `w`에 대해 `변위=w·A·sin(ωt+φ)`를 더할 수 있다. 위상 `φ`를 전부 같게 하면 풀 전체가 판처럼 흔들린다. 풀 한 포기의 상단 정점은 같은 변위를 주고 포기별 위상을 달리하면 폭의 변형을 줄이면서 반복을 완화할 수 있다. 이는 [GPU Gems 7장의 군집·정점·풀 단위 비교](https://developer.nvidia.com/gpugems/gpugems/part-i-natural-effects/chapter-7-rendering-countless-blades-waving-grass)를 참고한 설명용 선택이다.

정적 bounds가 바람으로 움직인 정점을 포함하지 않으면 화면 안의 끝부분까지 잘못 컬링될 수 있다. 최대 변형 범위를 미리 포함하거나 변형에 맞춰 bounds를 갱신한다. [Unity Renderer.localBounds](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Renderer-localBounds.html)도 사용자 정점 변형 셰이더에서 기본 bounds가 부정확할 수 있음을 설명한다. 반대로 과도한 bounds는 컬링의 이득을 줄인다. 동일 카메라 경로에서 최적화를 하나씩 바꾸고 누락·LOD 전환·그림자까지 함께 관찰해야 한다. 현재 브라우저·엔진 성능 비교는 미실행이다.
