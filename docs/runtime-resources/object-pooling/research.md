# 오브젝트 풀 자료와 채택 판단

[상세 분석](analysis.md) · [그룹 요약](../README.md)

기존 검토 기록은 2026-09-23의 `valid` 판정이다. 2026-09-25 아래 공식 본문을 열람해 API 동작 근거를 확인했다.

아래 2026-09-25 공식 문서 열람은 작성 단계의 기록이다. 이어진 교차검토에서는 공개 본문을 다시 열지 않고, 풀 꺼내기와 재대여의 집계 기준·마지막 반환 시각·사전 준비 절차를 다시 계산해 구체화했다.

## 조사 대상과 범위

수집 ID `object-pooling`은 2026-09-22에 Unity의 풀 API를 대상으로 시작한 웹 조사다. 2026-09-25에는 기존 설명·후속 과제와 아래 공식 본문을 대조했다. 영상 분석이나 출시 게임 측정에서 시작한 항목은 아니다.

탄환 번호·사용 중/대기 중 상태·발사율 조작은 실행 결과가 아니라 관찰 설계다. 상세 문서는 이를 수명 상태와 호출 수 계산으로 풀어 썼다. 이 문서의 API 표와 계산 조건만으로 채택 이유를 확인할 수 있다.

## 기존 설명에서 유지하거나 구체화한 부분

- **구체화:** 보관 한도 초과로 풀에서 제외하는 것과 실제 GameObject 파괴는 다르다. 공식 예시의 `OnDestroyPoolObject`처럼 제공한 콜백에서 `Destroy`를 호출해야 한다.
- **유지:** 보관 수는 동시 사용 수 제한이 아니다. 풀 크기를 조절해도 발사를 거부하는 별도 정책이 없다면 객체는 더 만들어질 수 있다.
- **구체화:** 원자료의 ‘사전 준비 수’는 `defaultCapacity`와 다른 개념으로 정의했다. 생성자 용량만 설정하고 준비가 끝났다고 표시하면 첫 요청의 생성 비용을 설명할 수 없다.
- **구체화:** 초기화 누락을 ‘이전 속도가 남는다’에 한정하지 않고, 예전 타이머가 새 대여 수명을 종료하는 자체 반례로 확장했다. 공식 API가 세대 번호를 제공한다는 주장은 하지 않았다.
- **보류:** 풀로 객체 생성을 줄인 사실만으로 GC 발생 횟수, GPU 비용, Unity와 웹 사이의 절감률을 계산하지 않는다.

상세 문서의 `20회/초 × 0.5초`, 생성 10회 대 1,200회, 풀 꺼내기 1,200회 중 최초 사용 10회·재대여 1,190회, 15개 요청/10개 보관 사례는 조건을 명시한 자체 산술이다. 공식 문서의 벤치마크를 옮긴 숫자가 아니다. 사전 준비와 발사 요청을 분리하고 마지막 반환까지의 관찰 구간을 명시했다. 요청 직후 반환을 반복하는 것과 여러 인스턴스를 먼저 확보하는 것도 다른 준비 절차다.

## 남은 질문

1. 대상 실험에서 짧은 객체 수명의 비용 중 생성·엔진 등록·메모리 할당·정리 비중은 얼마인가?
2. 수명 만료와 충돌을 같은 스텝에 배치했을 때 한 번만 반환되는가? 이전 수명의 비동기 작업이 다음 수명을 건드리지 않는가?
3. 준비 시간까지 포함한 전체 사용 세션에서 풀의 크기를 키우는 것이 실제로 유리한가?

이 질문은 확인 과제이며 통과 기록이 아니다. 공식 발사체 예제는 특정 출시 게임의 구현 사례로 사용하지 않는다.
