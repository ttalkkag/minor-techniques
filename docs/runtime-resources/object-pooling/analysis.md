# 짧은 객체 수명과 반복 생성 비용

[그룹 요약](../README.md) · [출처와 판단](research.md)

탄환이 0.5초 만에 사라져도 생성에 필요한 작업은 실행된다. 같은 모양의 탄환을 매번 새로 만드는 경우, 동시에 존재하는 수는 적지만 한 분 동안 거쳐 간 객체 수는 많다. 오브젝트 풀은 이 둘을 분리한다. 현재 사용하지 않는 인스턴스를 보관하고 다음 발사에서 다시 사용한다.

## 생성 횟수와 동시 사용량

발사율을 `r`회/초, 수명을 `L`초로 고정하면 정상 상태의 동시 탄환 수는 대략 `rL`개다. 관찰 기간 `T`초 동안 매번 생성하는 방식은 약 `rT`개를 생성한다. 경계 시각의 발사·반환 순서에 따라 한 개 차이가 날 수 있다.

자체 계산 예시로 0초부터 60초 미만까지 0.05초 간격으로 발사하고 수명을 0.5초로 두자. 충돌로 조기 종료하지 않고 같은 시각의 반환을 다음 요청보다 먼저 처리한다면 최대 동시 사용은 10개, 총 발사는 1,200회다. 미리 만든 10개를 풀에서 꺼내는 횟수는 1,200회지만 최초 사용 10회와 이전 발사에 썼던 객체의 재대여 1,190회는 구별한다. 준비용 요청·반환은 발사 요청에 포함하지 않는다. 마지막 발사의 반환까지 세려면 관찰을 60.45초까지 이어간다. 이는 호출 수 계산이며 CPU 시간이나 GC 절감률 측정이 아니다.

풀 사용 비용은 다음처럼 나눠 생각할 수 있다. 각 비용은 대상 환경에서 따로 측정해야 한다.

```text
매번 생성 = 발사 수 × (생성 + 등록 + 사용 후 정리)
풀 사용   = 사전 준비 비용 + 발사 수 × (꺼내기 + 초기화 + 반환)
추가 보관 메모리 = 대기 객체의 실제 점유량 합계
```

이 비용식은 풀 부족으로 추가 생성하지 않고 모든 발사체가 반환될 때까지의 단순 모델이다. 사전 준비 비용에는 객체 생성과 준비용 요청·반환 작업도 들어간다. 꺼내기·반환이 공짜가 아니고, 객체를 사용 중인 동안의 충돌·이동·렌더링도 그대로다. 생성이 드물거나 초기화가 비싸면 풀을 추가해도 이득이 작을 수 있다.

## 수명 상태를 분리해야 재사용이 안전하다

한 인스턴스는 `대기 → 사용 중 → 반환 처리 → 대기 또는 파괴` 순서를 따른다. 발사에 필요한 위치·방향·속도는 사용을 시작할 때 설정하고, 이전 발사에서 살아 있는 이벤트·타이머·코루틴·파티클은 반환 단계에서 끝낸다. Unity 문서도 물리·애니메이션 상태 및 진행 작업의 초기화를 별도로 다룬다. [Unity의 상태 초기화 절](https://docs.unity.com/en-us/engine/6000.0/manual/scripting/optimization/performance-optimizing-code-managed-memory/reusable-code)

예를 들어 탄환 7번이 표적에 맞아 반환된 뒤 즉시 재발사됐는데, 이전 발사의 수명 타이머가 뒤늦게 실행되면 새 발사까지 반환할 수 있다. 단순히 위치를 바꾸는 것으로는 막을 수 없다. 설계상 이전 타이머를 취소하거나, 대여할 때 증가시킨 세대 번호를 콜백이 확인하도록 할 수 있다. 이 세대 번호는 자체 설계 예시이며 Unity 풀 API가 자동 제공한다는 뜻은 아니다.

충돌과 수명 만료가 같은 스텝에서 발생하는 경우도 같은 수명에 대해 종료 결정을 한 번만 내려야 한다. 두 콜백 모두 `Release`를 호출하면 대기 목록과 사용 중 목록이 모순될 수 있다. 개발 도구의 중복 반환 검사와 제품 코드의 종료 상태 관리는 역할이 다르다.

## 보관 한도와 발사 한도

Unity `ObjectPool<T>`에서 빈 풀의 `Get`은 생성 콜백을 호출하며, 꽉 찬 풀에 반환한 객체는 파괴 콜백의 대상이다. 따라서 `maxSize=10`만으로 11번째 동시 발사를 막는다고 해석하면 안 된다. [Unity의 요청·반환 설명](https://docs.unity.com/en-us/engine/6000.0/manual/scripting/optimization/performance-optimizing-code-managed-memory/reusable-code)

이때 풀에서 제외하는 것과 Unity GameObject를 파괴하는 것은 구별한다. 실제 `Destroy` 호출 등 자원 정리는 제공한 `actionOnDestroy` 콜백이 담당한다.

교육 예시에서 초과 반환을 파괴하는 콜백을 제공하고 보관 한도를 10개로 둔 뒤 15발을 한꺼번에 요청하면 15개가 사용될 수 있다. 모두 반환할 때 10개를 남기고 5개를 파괴한다. 다음에 다시 15발이 필요하면 5개를 추가 생성한다. 최대 보관량만 작은 풀은 폭발적인 요청 구간마다 생성 비용이 재발할 수 있다.

`defaultCapacity`도 사전 생성 수와 다르다. 내부 보관 구조의 초기 용량이며 빈 풀에 `Get`을 호출할 때 인스턴스가 만들어진다. 준비 수만큼 먼저 요청해 서로 다른 인스턴스를 확보한 뒤 한꺼번에 반환하는 방식으로 준비할 수 있다. 요청하자마자 반환하는 동작을 10번 반복하면 같은 인스턴스 하나만 계속 꺼낼 수 있으므로 10개 준비와 같지 않다. 준비용 요청에서도 콜백이 실행되는 조건과 최대 보관량을 함께 맞춰야 한다. [Unity 생성자 매개변수](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Pool.ObjectPool_1-ctor.html)

| 조건 | 선택할 정책 | 바뀌는 결과 |
| --- | --- | --- |
| 발사 결과를 반드시 보존해야 함 | 부족하면 추가 생성 | 갑작스러운 생성 비용을 허용 |
| 이펙트 수를 제한해도 됨 | 요청을 거부하거나 우선순위 낮은 효과 생략 | 표시 밀도가 달라지므로 동일 동작 비교에서 분리 |
| 대략적인 최고 동시 사용량을 앎 | 그 수만큼 사전 준비 | 초기 준비 시간과 메모리 증가 |
| 구간마다 필요량이 크게 다름 | 구간 종료 뒤 대기 객체 정리 | 다음 구간에서 다시 준비할 수 있음 |

## 관찰에서 분리할 값

고유 객체 번호와 대여 번호를 따로 표시하면 같은 인스턴스의 새 수명을 구별할 수 있다. 발사 수, 신규 생성 수, 재사용 수, 사용 중 수, 대기 수, 파괴 수를 센 뒤 같은 입력에서 충돌 결과가 동일한지 확인한다. 프레임 시간 변화만으로 GC가 원인이라고 결론 내리지 않는다. Unity C# 객체와 브라우저 JavaScript/WebGL 자원의 수명도 같지 않다.

위 계산과 상태 전이는 분석용 모델이다. 프로파일러 실측, 중복 반환 재현, 브라우저별 메모리 비교는 아직 수행하지 않았다.
