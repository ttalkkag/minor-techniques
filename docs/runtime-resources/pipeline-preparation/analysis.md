# 처음 사용하는 렌더링 조합의 준비 지연

[그룹 요약](../README.md) · [출처와 판단](research.md)

매 프레임 그리는 작업이 가벼워도 첫 번째 마법이나 처음 보는 재질에서만 화면이 멈출 수 있다. 필요한 GPU 실행 코드·파이프라인 상태가 처음 사용되는 시각까지 준비되지 않은 경우다. 이 문제는 이미 준비된 효과를 매 프레임 많이 그리는 문제와 원인이 다르다.

## 셰이더 이름 하나로 준비 여부를 판단할 수 없는 이유

여기서 다루는 지연은 PC·모바일처럼 실행 장치의 드라이버가 GPU 코드를 준비하는 경로를 중심으로 한다. Epic의 2025년 글은 고정 GPU를 대상으로 셰이더 실행 코드를 미리 배포하는 콘솔 경로를 구별하므로, 모든 플랫폼에서 같은 최초 컴파일 비용이 발생한다고 일반화하지 않는다.

PSO는 셰이더뿐 아니라 깊이·블렌딩 등 렌더링 상태를 함께 묶는다. 같은 재질이 본체·그림자·깊이 패스에 참여하면 필요한 조합도 하나가 아닐 수 있다. Epic은 플레이 기록으로 조합을 모으는 방식과 로드한 자원·컴포넌트에서 가능한 조합을 예상하는 방식을 구분한다. [Epic 개발팀 설명](https://www.unrealengine.com/tech-blog/game-engines-and-shader-stuttering-unreal-engines-solution-to-the-problem)

자체 조합 예시로 셰이더 변형 4개, 정점 형식 2개, 블렌딩 상태 3개를 모두 자유롭게 결합하면 후보는 `4×2×3=24개`다. 실제 유효 조합이 10개이고 한 장면에서 쓰는 조합이 3개일 수도 있다. 전부 준비하는 정책은 누락을 줄이는 대신 사용하지 않는 후보에 비용을 쓴다. 플레이 중 본 것만 준비하면 비용은 줄지만 새 조합을 처음 만났을 때 대기가 남는다. 실제 엔진 조합 수를 이 곱셈 예시로 추정하지 않는다.

## 요청 시각과 사용 시각을 분리한다

조합 하나에 대해 다음 네 시각을 기록한다.

```text
t_request : 준비 요청
t_start   : 작업이 실제 시작됨
t_ready   : 준비 완료
t_need    : 처음 그려야 하는 시각
대기 시간 = max(0, t_ready - t_need)  (성공할 필수 조합 하나를 기다리는 정책)
```

모의 사례에서 작업 자체가 40ms 걸린다고 하자. 0ms에 요청했지만 다른 작업 때문에 20ms에 시작하면 완료는 60ms다. 최초 필요 시각이 50ms면 10ms 늦는다. 요청 자체가 빠르다는 것과 필요한 시각에 완료됐다는 것은 다르다. 사전 요청을 누락하면 최초로 필요해진 시점에야 요청할 수 있다. 실패한 작업에는 사용 가능한 `t_ready`가 없으므로 이 대기 시간식 대신 실패·대체 표시 경로를 적용한다.

| 관찰 | 가능한 원인 | 먼저 바꿀 것 |
| --- | --- | --- |
| 필요한 조합이 준비 목록에 없음 | 수집 누락 또는 잘못된 조합 추정 | 대상·상태 식별과 수집 경로 |
| 요청은 있으나 완료가 늦음 | 요청 시점, 작업 대기열, 동시 작업량 | 먼저 요청하거나 경쟁 작업량 조절 |
| 완료 뒤에도 최초 사용에서 지연 | 캐시 재조회 등 다른 단계 | 준비 완료와 실제 사용 구간을 나눠 추적 |
| 준비 실패 | 컴파일/링크 실패 등 | 실패 정보와 대체 표시 처리 |

Epic의 `Missed`와 `Too late`는 앞의 두 행을 구분하는 진단이다. ‘미리 준비했다’ 하나로 합치면 누락된 대상을 늘릴지 작업 스케줄을 조절할지 판단하기 어렵다. [Epic Validation and Tracking](https://dev.epicgames.com/documentation/en-us/unreal-engine/pso-precaching-for-unreal-engine)

## 준비가 끝나기 전 무엇을 보여줄 것인가

화면을 기다리게 하면 표현의 일관성을 유지하지만 프레임 진행이 끊긴다. 객체 표시를 늦추면 장면 일부가 나중에 나타나고, 기본 재질로 대신 그리면 형태는 먼저 보이지만 외형이 달라진다. 초기 로딩 단계에서 기다리면 게임 중 대기를 줄이는 대신 시작 시간이 길어진다. 어떤 정책이든 비용의 발생 시점이나 화면 결과가 달라진다. [Epic Component PSO Precaching와 Loading screen](https://dev.epicgames.com/documentation/en-us/unreal-engine/pso-precaching-for-unreal-engine)

준비한 조합을 모두 메모리에 남기는 선택도 별도다. 드라이버 캐시가 존재해도 다시 가져오는 작업이 무료라고 가정할 수 없다. 반대로 상주량을 늘려 사용 시 재조회 비용을 줄이면 메모리 예산을 더 쓴다.

## 웹에서 같은 원리를 다루는 범위

WebGL 프로그램은 Direct3D/Vulkan PSO와 같은 객체가 아니다. `KHR_parallel_shader_compile`은 완료 여부를 비차단 방식으로 확인하는 확장이다. 완료를 확인한 뒤 성공 여부를 검사해야 하며, 완료와 성공을 같은 상태로 표시하면 실패 사례가 사라진다. 총 컴파일 시간이 줄어든다는 약속도 아니다. [Khronos 확장 Overview와 Sample Code](https://registry.khronos.org/webgl/extensions/KHR_parallel_shader_compile/)

실험에서는 조합 ID, 요청·시작·완료·최초 사용, 준비 중 대체 화면을 연결하면 원인을 볼 수 있다. 조절한 고정 지연은 모의 시간으로 다루고 실제 WebGL 측정과 분리한다. 재방문이 빠르다는 사실만으로 특정 캐시나 셰이더를 원인으로 확정하지 않는다. 이 문서 작성에서는 WebGL 실행·캐시 초기화·드라이버 성능 측정을 하지 않았다.
