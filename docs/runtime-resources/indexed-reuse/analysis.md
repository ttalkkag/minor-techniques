# 팔레트와 타일: 반복 데이터 대신 번호 저장하기

[그룹 요약](../README.md) · [출처와 판단](research.md)

같은 색이 반복되는 이미지와 같은 무늬가 반복되는 배경은 공통 데이터 한 번과 각 위치의 번호로 나눌 수 있다. 팔레트는 색을 공유하고 타일맵은 작은 그림을 공유한다. 둘 다 간접 참조로 중복을 줄이는 방식이므로 함께 분석하되, 픽셀 색 번호와 타일 번호를 같은 단위로 세지 않는다.

## 팔레트의 절감량에는 색 표도 포함된다

픽셀 수 `P`, 사용 색 수 `K`, 인덱스 깊이 `b=ceil(log2 K)`라고 하자. 2색 이상이고 행 경계 정렬을 생략한 자체 포맷의 기본 비용은 다음과 같다.

```text
RGB24    = 3P 바이트
인덱스형 = ceil(Pb/8) + 3K 바이트
```

13색을 쓰는 16×16 이미지에서 `P=256`, `b=4`다. RGB는 768바이트, 인덱스는 128바이트, RGB 팔레트는 39바이트여서 합계 167바이트다. 인덱스만 비교한 `768/128=6배`와 전체 기본 표현을 비교한 `768/167≈4.60배`는 다르다. 헤더·투명도·정렬까지 넣으면 결과가 다시 달라진다.

이 예시 포맷은 색 번호 0~12를 사용한다. 원영상 그림의 번호 1~13은 설명 표기의 선택이며 PNG 인덱스 정의와 혼합하지 않는다. PNG의 인덱스 컬러는 1·2·4·8비트 중 가능한 깊이를 사용하고, RGB 팔레트는 별도 `PLTE`에 저장한다. [W3C PNG 11.2.1·11.2.2](https://www.w3.org/TR/png-3/)

팔레트만 교체하면 같은 번호 배열로 다른 색 조합을 만들 수 있다. 하지만 같은 번호가 쓰인 모든 위치가 함께 바뀐다. 특정 한 픽셀만 독립적으로 색을 바꾸려면 다른 번호를 배정하거나 원본 번호 배열을 수정해야 한다. 공유라는 장점과 수정 범위의 제약이 같은 구조에서 생긴다.

## 타일맵도 원본 그림과 위치 표를 함께 센다

한 타일의 원시 크기가 `S`, 고유 타일 수가 `U`, 배치 칸 수가 `N`, 칸마다 사용하는 번호 크기가 `I`바이트라면 기본 비교는 다음과 같다. `I`는 양의 정수이고 고유 타일을 모두 가리킬 수 있어야 하므로 `U≤2^(8I)`를 만족한다고 가정한다. 두 방식에서 동일하게 필요한 팔레트·속성 비용은 같은 범위로 센다.

```text
공통 비용 = 두 표현에 동일하게 드는 팔레트·속성 등
칸마다 복사 = NS + 공통 비용
타일 재사용 = US + NI + 공유 방식에만 추가되는 속성 비용 + 공통 비용
```

자체 예시로 8×8·2비트 타일은 `S=16바이트`다. 배치 100칸, 고유 타일 10개, 1바이트 번호와 12바이트 팔레트를 사용하고 속성 표를 생략하면 복사 방식은 `1,600+12=1,612바이트`, 공유 방식은 `160+100+12=272바이트`다. 고유 타일이 100개라면 공유 방식은 `1,600+100+12=1,712바이트`로 오히려 커진다. 이는 NES의 실제 메모리 배치가 아닌 동일 범위의 자체 표현 비교다.

같은 비용 항목이 양쪽에 존재한다면 중복 제거가 유리할 조건은 `(N-U)S > NI + 추가 속성 비용`이다. 공유할 무늬가 많을수록 유리하지만 번호를 저장하는 비용은 남는다. 타일 원본을 수정하면 그 번호를 사용하는 모든 칸에 영향이 간다는 점도 팔레트와 같다.

## 역사적 수치를 해석할 때 빠지는 항목

고전 그래픽 영상의 `960+64=1,024바이트`는 배치와 속성 설명이다. 타일 원본·팔레트가 빠져 있으므로 완성된 배경 그림 전체를 1KiB(1,024바이트)에 넣었다는 계산으로 사용하지 않는다. 같은 영상의 256×240 화면을 64색의 조밀한 6비트 인덱스로 계산하면 `256×240×6/8=46,080바이트`다. 약 70KB·70배라는 비교는 저장 가정과 비용 범위가 맞지 않아 채택하지 않는다. [영상과 정정 근거](research.md)

NESdev 본문 접근 제한이 남아 있어 구체적인 주소·사이클·매퍼의 동작을 이번 문서에서 확정하지 않는다. 타일 원본과 번호를 분리하는 교육 모델은 유지하되, 모드별 하드웨어 사양은 별도 조사 대상이다.

## 파일 크기와 실행 메모리는 다른 결과다

PNG 파일에는 필터·압축·청크가 추가된다. 복원 뒤 RGBA 배열로 바꾸거나 다른 GPU 형식으로 업로드하면 인덱스 표현의 크기가 그대로 유지되지 않는다. [W3C PNG 9·10·11.2.3](https://www.w3.org/TR/png-3/)

따라서 비교는 다음 네 단계를 독립적으로 기록해야 한다.

1. 자작 그림의 원시 픽셀 또는 타일 배열 크기.
2. 팔레트·번호·속성·행 정렬을 포함한 저장 표현 크기.
3. 실제 저장 파일의 전체 바이트 수.
4. 복원 배열과 GPU에 올린 실제 형식 및 점유량.

픽셀 색 수 제한이나 무늬 공유가 목적이면 인덱스 모델이 적절하다. 큰 텍스처 배포가 목적이면 KTX/Basis 같은 별도 경로를 비교할 수 있으나, 픽셀 아트 색 보존과 팔레트 교체에 적합한지는 별도 확인이 필요하다. [Khronos KTX 개요](https://www.khronos.org/ktx/)

무손실 비교에서는 원본과 복원 픽셀을 전부 대조하고, 손실 양자화를 선택했다면 크기뿐 아니라 달라진 색도 보여줘야 한다. 여기의 수식은 자체 산술이며 파일 인코딩·GPU 메모리·원작 ROM을 측정한 결과는 아니다.
