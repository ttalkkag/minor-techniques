기존 검토는 2026-09-23 `historical`이다. 이번 원자료 정리와 인터뷰 본문 열람은 2026-09-25에 수행했다. 개발자의 설명과 실행 환경에서의 실측은 구분한다.

아래 2026-09-25 인터뷰 열람은 작성 단계의 기록이다. 이어진 교차검토에서는 실제 경로 길이와 양의 속도, 준비 단계가 순차적일 때만 시간을 더할 수 있다는 전제를 보강했다. 인터뷰를 다시 열거나 원작을 측정하지 않았다.

## 조사 대상과 출처의 성격

수집 ID `jak-world-streaming`은 2026-09-22 개발자 인터뷰를 토대로 한 웹 조사다. 이후 두 인터뷰의 직접 발언과 청크 상태·순간이동·관찰 카메라에 관한 자체 모델을 구분했다. 원작 엔진 코드나 메모리 덤프를 확보한 조사는 아니다.

GamesRadar+는 기술 명세의 제작사가 아니지만 이 부분은 저자가 Gavin에게 직접 들은 발언을 싣고 있어 개발자 증언의 원출처로 사용한다. 기사에 등장하는 다른 게임의 모든 로딩 장치 추정까지 1차 증언으로 취급하지 않는다.

## 원자료에서 압축돼 있던 조건 복원

GamesRadar+ 발언은 단순히 ‘두 청크를 넣었다’에서 끝나지 않는다. 동시에 두 청크를 넘게 보거나 점유하지 않도록 하고, 교체 사이에 단일 청크만 필요한 구간을 확보했다고 설명한다. 이 조건을 빼면 다음 데이터를 담을 공간이 어디서 생겼는지 이해할 수 없다. 상세 문서의 A→B→C 상태 순서는 그 설명을 풀어 쓴 자체 도식이다.

같은 발언의 청크 읽기 약 8~10초, 교체를 위한 읽기 시간의 두 배 언급은 당시 개발자 회고의 근삿값으로만 보존한다. 실측 수치나 모든 경로에 적용할 설정값으로 채택하지 않는다. 상세 문서의 `30m / 6m/s` 사례는 원작과 별개인 산술 예시다. 경로 길이와 양의 속도, 순차 처리 시간 합산의 전제를 명시했으며 읽기·복원이 겹치면 실제 요청부터 완료까지의 경과 시간으로 비교한다.

PlayStation 인터뷰의 최초 사례 주장도 그대로 역사적 사실로 확정하지 않는다. 이 항목의 목적은 최초 발명자를 정하는 것이 아니라, 데이터 준비에 레벨 형태와 이동 속도가 관여하는 원인을 설명하는 데 있다.

## 채택 판단과 미확인 항목

- **채택:** 로딩 표시가 없어도 읽기 작업은 존재한다. 청크 교체와 플레이어의 다음 필요 시점이 맞아야 한다.
- **채택:** 개발자 직접 발언에 나오는 경로·시야 제약을 해당 작품의 역사적 사례로 사용한다.
- **교육적 확장:** 준비 시간에 대기열·읽기 이후 처리 시간을 따로 더하고 임시 메모리를 계산하는 모델은 일반화된 설계 설명이다. 원작이 그 항목별 시간을 기록했다는 주장은 아니다.
- **미확인:** 두 청크 바깥의 공유 데이터·음원·먼 배경, 실제 파일 배치, 방향 전환 시 유지 정책, 시작·사망·순간이동의 세부 처리.

기존 과제인 고정 경로 기록, 느린 읽기와 순간이동 반례, 관찰 카메라 독립성 확인은 실행하지 않았다. 이 과제들의 예정된 결과를 작품의 성능 증거로 사용하지 않는다.
