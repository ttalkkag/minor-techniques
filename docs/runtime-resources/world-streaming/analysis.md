# 이동보다 늦게 준비되는 월드 데이터

[그룹 요약](../README.md) · [출처와 판단](research.md)

월드 전체를 메모리에 올릴 수 없다면 현재 필요한 부분과 다음에 필요할 부분을 골라 유지해야 한다. 화면에 로딩 표시가 없어도 저장장치 읽기와 자원 준비는 계속된다. 문제가 드러나는 시점은 플레이어가 아직 준비되지 않은 지역을 보거나 사용하려 할 때다.

## 데이터 교체와 이동 경로의 관계

Jak and Daxter 공동 제작자 Andy Gavin은 DVD 심리스 로딩을 개발했다고 회고했다. 별도 직접 인터뷰에서는 가용 메모리를 두 청크로 나누고, 동시에 필요한 청크 수와 청크 사이 이동 시간에 제약을 두었다고 설명한다. 청크 경계를 굽게 만들거나 문·거리를 활용했다는 설명도 있다. [PlayStation 인터뷰](https://blog.playstation.com/archive/2017/08/24/extended-play-how-naughty-dog-went-from-crash-to-jak-daxter/), [GamesRadar+의 Gavin 직접 발언](https://www.gamesradar.com/the-secret-art-of-the-video-game-loading-screen-and-why-they-wont-be-going-away-anytime-soon/)

이를 자체 상태 모델로 풀면 다음 순서다.

1. A 지역에 있는 동안 다음 B 데이터를 요청한다.
2. A를 계속 사용하면서 B를 읽고 준비한다.
3. A와 B가 함께 필요한 경계 구간을 지난다.
4. A가 더는 필요하지 않은 지점에서 A를 내린다.
5. 빈 공간에 C를 준비하고 B→C 경계 전에 완료한다.

이 순서는 ‘보이지 않는 즉시 해제’와 같지 않다. 돌아가거나 멀리 보는 조건 때문에 이전 데이터가 계속 필요할 수 있다. 가시성·충돌·게임 상태가 필요로 하는 범위를 정한 뒤 해제할 시점을 선택해야 한다. 두 청크는 인터뷰를 이해하기 위한 단순 모델이며 원작의 오디오·공통 자원·먼 배경까지 두 덩어리였다는 주장은 아니다.

## 시간 조건을 계산하는 방법

요청 지점부터 최초 필요 지점까지 실제 이동 경로의 길이 `d≥0`, 일정 이동 속도 `v>0`라면 사용 가능 시간은 `d/v`다. 여기서 최초 필요 지점은 반드시 입구가 아니다. 멀리서 보이는 지형이라면 입구 도착 전에 준비돼야 한다.

```text
준비 시간 = 대기열 시간 + 읽기 시간 + 읽은 뒤 필요한 준비 시간 (순차 처리 모델)
시간 여유 = t_need - t_ready
일정 속도 이동의 여유 = d/v - 준비 시간
```

읽기와 복원·업로드가 일부 겹치는 구현에서는 단계별 시간을 그대로 더하면 중첩 시간을 두 번 셀 수 있다. 그때는 요청부터 실제 사용 가능 상태까지의 경과 시간 `t_ready-t_request`를 사용한다.

자체 예시로 `d=30m`, `v=6m/s`, 전체 준비가 `4초`라면 여유는 `1초`다. 속도를 `12m/s`로 올리면 필요 시각이 `2.5초`로 앞당겨져 `1.5초` 늦는다. 길을 그대로 두고 시야만 가려도 충돌 데이터가 필요한 시점은 바뀌지 않을 수 있다. 반대로 굽은 길이 실제 이동 거리를 늘리면 준비 시간도 확보할 수 있다.

| 조절 | 직접 바뀌는 것 | 남는 조건 |
| --- | --- | --- |
| 요청 지점을 앞당김 | 준비를 시작할 여유 | 현재 자원과 함께 보관할 메모리 필요 |
| 통로를 길게 함 | 다음 사용까지 이동 시간 | 빠른 이동·우회 경로도 고려 |
| 시야를 막음 | 렌더링에 처음 필요한 시점 | 충돌·AI 등 다른 사용은 남을 수 있음 |
| 청크를 작게 함 | 한 번에 교체할 데이터 | 요청 빈도·경계 수가 늘 수 있음 |
| 이동 속도를 제한함 | 사용 시점 | 조작감과 게임 규칙에 직접 영향 |
| 입구에서 기다림 | 미준비 영역 진입 방지 | 플레이 흐름이 멈춤 |

표는 원리에서 도출한 선택지이며, 각각을 원작이 실제 채택했다고 의미하지 않는다.

## 메모리 조건도 동시에 만족해야 한다

현재 청크를 유지하는 동안 다음 청크를 읽으려면 두 작업이 함께 차지할 공간이 필요하다. 단순 모델의 조건은 다음과 같다.

```text
현재 청크 + 다음 청크 + 공통 자원 + 작업용 임시 공간 ≤ 메모리 예산
```

읽은 압축 데이터와 복원 결과를 동시에 들고 있는 설계라면 둘을 따로 세야 한다. 요청을 아주 일찍 해도 공간을 확보하지 못하면 작업이 대기할 수 있다. 반대로 공간을 먼저 비우려다가 플레이어가 되돌아오면 방금 버린 지역을 다시 읽게 된다. 이동 시간만 계산한 모델로 이 문제를 설명할 수 없다.

## 예측이 깨지는 경우

방향 전환은 다음 청크 예상을 바꾸고, 순간이동은 확보했던 이동 시간 자체를 없앤다. 대응은 이전 청크를 잠시 더 보관하기, 후보를 여러 개 준비하기, 순간이동 중 전환 화면을 두기처럼 서로 다른 비용을 가진다. 이를 원작의 알려진 버그나 실제 해결 코드라고 적지 않는다.

관찰 도식에는 청크별 요청·준비 완료·최초 필요·해제 시각과 메모리 점유를 표시한다. 자유 관찰 카메라는 데이터가 없는 지역까지 보여줄 수 있지만, 그 카메라의 움직임이 플레이어용 요청을 추가하면 비교 조건이 달라진다. 플레이 시점과 설명 시점의 역할을 분리한다.

이 문서는 인터뷰와 자체 시간·공간 모델의 분석이다. 원작 DVD 속도, 실제 메모리 배치, 브라우저 네트워크 스트리밍 성능은 측정하지 않았다.
