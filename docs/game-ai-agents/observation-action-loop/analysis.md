# 낡은 관측과 실행 결과 누락 — 상세 분석

## 실패가 생기는 순서

게임 월드는 계속 변하지만 에이전트가 받은 화면은 특정 시점의 복사본이다. 예를 들어 `맵 A, 프레임 100, 좌표 (4,3)`에서 이동을 계획했는데 추론 중 전투가 시작되면, 버튼 전송에 성공해도 원래 목적지로 이동한 것이 아니다. 이동 함수의 반환, 게임 상태 변경, 목표 완료는 각각 다른 사건이다.

속도 표시나 움직임 단서가 없는 정지 화면 한 장만으로는 같은 위치의 공이 왼쪽으로 가는지 오른쪽으로 가는지 확정할 수 없다. 앞뒤 관측을 비교하더라도 모두 오래됐거나 순서가 뒤바뀌면 현재 상황을 알 수 없다. 관측 나이는 동일한 시계 기준에서 `판단 시각 - 캡처 시각`으로 구한다. 캡처와 판단이 다른 장치에서 이뤄지면 시계 차이를 먼저 보정하거나 같은 시간축으로 기록해야 한다. 캡처 시각을 전송 시각으로 대신하면 캡처 후 대기 시간을 숨긴다.

포켓몬의 소포 전달 사례는 또 다른 상태 누락이다. '오박사에게 배달한다'는 기억이 남아 있어도 현재 목표를 '전달 완료 후 다음 행동'으로 갱신하지 않으면 이전 계획을 반복한다. Minecraft 동료의 행동·대사 모순도 같은 경계에서 생긴다. 한 모듈은 공격을 실행하고 다른 모듈은 사용자 요청에 거절 대사를 만들면 둘 다 각자의 입력에는 맞지만 전체 결과는 충돌한다.

## 상태를 나누는 해결 과정

1. 관측을 `observation_id, captured_at, map_id, state`로 보관한다. 자체 게임의 좌표·체력·인벤토리와 화면 추론은 출처를 구분한다.
2. 행동 요청에 관측 ID, 대상 맵, 완료 조건, 최대 행동 길이를 붙인다. 실행 직전에 맵이나 대상이 달라졌으면 오래된 요청을 다시 판단한다.
3. 한정된 행동을 실행하고 새 관측을 얻는다. 실행 결과에는 성공 여부뿐 아니라 실제 바뀐 좌표·아이템과 중단 사유를 넣는다.
4. 완료 조건이 충족됐을 때 현재 목표를 갱신한다. 과거 경험 검색은 다음 계획을 도울 수 있지만 완료 판정을 대신하지 않는다.
5. 캐릭터의 완료 대사는 이 실행 결과를 입력으로 만든다. 실행 전에는 의도만 말하고, 실패 후에는 실패한 부분을 설명한다.

이 분리는 [제작자 저장소의 계획·결정적 실행·결과 해석 구조](https://github.com/sesang06/pokemon_red_ai)를 참고한 설계다. 모든 역할을 LLM으로 구현해야 한다는 뜻은 아니다.

## 건축에서 부분 성공을 다루는 예

벽 10칸 중 6칸만 배치됐다면 작업 전체를 그대로 재실행하지 않는다. 요청 청사진과 현재 블록을 대조해 남은 4칸을 구한다. 자원 수량·좌표 범위·허용 블록을 배치 전에 확인하고, 완료 판정은 실제 월드와 청사진의 차이로 한다. 되돌릴 때는 이 작업의 변경 전후 상태를 보관하고, 현재 블록이 이 작업 직후 상태와 여전히 일치하는지 확인한다. 다른 작업이 같은 좌표를 수정했다면 자동 복원을 건너뛰고 충돌로 남긴다. 버전 번호를 함께 비교하면 다른 작업이 바꿨다가 같은 값으로 돌린 경우도 구분할 수 있다. 변경한 좌표 목록만으로는 동시 작업의 결과를 보호할 수 없다. 이는 원영상 코드의 동작을 확인한 설명이 아니라 부분 실행 문제를 위한 자체 설계 예다.

직접 블록을 바꾸는 편집 모드에서는 이동·채집 비용이 없다. 이를 생존 모드와 같은 완료 시간으로 비교하면 건축 계획과 게임 조작 중 어느 부분이 좋아졌는지 알 수 없다.

## 적용 범위와 대가

짧게 행동할수록 전환에 빨리 대응하지만 관측·모델 호출이 늘어난다. 반복 이동은 결정적 실행기에 맡기고 전투·맵 전환·실패 때 다시 계획하는 방법을 비교할 수 있다. 화면만 접근 가능한 외부 게임에서는 RAM·엔진 상태 확인 수준의 완료 보장을 할 수 없다.

설명 화면은 2D 격자와 세 개의 기록(실제 상태, 받은 관측, 실행 결과)으로 충분하다. 관측 지연과 한 번에 이동할 칸 수를 바꾸면 잘못된 완료 판정과 반복 이동의 원인을 볼 수 있다.
